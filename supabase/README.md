# Database setup and verification

Create a free Supabase project and apply every file in `supabase/migrations` in filename order using the Supabase CLI (`supabase db push` for a linked project) or the private project SQL editor. Migrations never contain real editor identities or credentials. Back up the database before changing an existing production schema; deploy the matching application after migrations succeed.

Disable public signup in Supabase Auth, then create exactly two password accounts using the private Auth dashboard's **Add user / Create user** operation. Set a strong password for each account and mark its email as confirmed in that trusted administrator flow. Set the site URL to your application's origin. This application uses email/password login; invitation links, password onboarding and `/auth/callback` are not implemented. Copy each created Auth user's UUID into `supabase/provision-editors.sql`, replace the display names, and run it in the private SQL editor. The script intentionally fails with placeholder UUIDs. No profile is created automatically on signup, and the browser has no provisioning capability. A unique active slot index plus the slot check allow at most two active editor profiles. See the root `SETUP.md` for the complete private administrator procedure.

Set the public project URL/anon key and server-only TMDB token in `.env.local` following the root `.env.example`. The service-role key is used only for server-controlled regional provider cache refresh. Editor content changes always execute with the real editor session. Do not put the service-role key into any `NEXT_PUBLIC_*` variable.

Run `npm run test:database` to execute production migrations against the embedded PostgreSQL engine PGlite. These are database tests using real roles, RLS, grants, foreign keys, checks, triggers and SQL transactions. The test bootstrap emulates only Supabase's JWT-to-SQL identity bridge and `auth.users`. It does not mock editor authorization. Tests cover anonymous/unknown/deactivated users, direct-write denial, two-editor limits, private notes, audit immutability, duplicate saves/restoration, watched state/history/corrections, exact rating steps, collections, metadata refresh, region caches, and transactional rollback on audit failure. A local Supabase smoke test remains necessary to verify the real Auth cookies/JWT bridge, PostgREST RPC dispatch and deployed project configuration.

Run `npm run db:types` to regenerate `src/types/database.ts` from the applied migrations' PostgreSQL catalogs. The generated file includes tables, views, enums, foreign keys and RPC signatures. It is reproducible without cloud access and identifies its PGlite catalog source. For comparison with a configured live Supabase project, run `npx supabase gen types typescript --linked` into a temporary file and review schema differences before replacing the committed types.

Public browse data comes from explicitly projected public views and `vault_public_data`. `vault_cached_movie` preserves safe TMDB metadata for removed-movie links. `vault_activity` provides bounded pagination and optional user/action/movie/collection/date filters; anonymous responses exclude note/preference events and before/after audit JSON. `vault_private_data` is available only to an approved editor and returns that editor's private notes and preferred region.

Direct content INSERT/UPDATE/DELETE privileges are revoked from both `anon` and `authenticated`. Editor RPCs use explicit active-editor checks, a fixed empty search path, validated inputs, deterministic row locking, and an atomic audit append. The internal helper schema is inaccessible to browser roles. Audit rows have a trigger preventing UPDATE/DELETE even through ordinary administrator SQL. Watch corrections preserve the old event and create a linked replacement; clearing current watched state never deletes history. Removing a movie or archiving a collection preserves its rows and historical relations.

RLS is enabled on every application table. Public table access is limited to safe metadata/relations, and private state/history reads use owner policies. All public state/history/activity views explicitly omit notes and emails. Public ratings and activity can be disabled by changing the respective `app_settings` values through a trusted administrator context.

Publicly readable metadata JSON is limited to known external fields. Movie metadata stores validated country names, projected spoken-language fields and a tagline; provider payloads store projected region/offer/link/fetched-time fields. Additional private-shaped keys supplied to the RPC are discarded, and audit identity comes from the authenticated database user rather than client-supplied actor metadata. Tests check both direct anonymous table/view reads and the application's actual Zod public DTO schemas.

On Windows, Vitest/esbuild may need a less restrictive filesystem sandbox to resolve the configuration through parent directories; this does not require database credentials or cloud access. PGlite is a development dependency only and is not part of the application runtime or paid infrastructure.
